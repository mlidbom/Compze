# Changelog

All notable changes to Compze.Teventive.MemoryImageStateStore will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/).

## 0.1.0-alpha

- **Documentation: files that accept non-atomic commits with a database commit after the database, whichever the database,** as `AcceptingNonAtomicCommitsWithADatabase()` now says. Before the versions of Compze.Sql.Sqlite and Compze.Sql.MySql whose connections commit as their transaction's decision, they committed before a SQLite or MySQL connection. And when the database's commit is in doubt, as when its connection breaks while it commits, the files don't commit, though the database may have, as `AcceptingNonAtomicCommitsWithADatabase()` now says too.
- **The memory image state store, a memory image of taggregates: every taggregate held in memory for the container's life, rebuilt at its start from a snapshot of each, which its storage keeps.** It keeps taggregates as their state, not their history. Composed with `MemoryImageStateStore(...)`, which declares the taggregate classes it keeps, each with a factory for empty instances, its indexes, and its storage.
  - Each unit of work gets a private copy of each taggregate it gets for update, and holds the taggregate's lock until it completes.
  - The tevents the copies publish are dispatched synchronously as each publish cascade ends, once the taggregate's invariants hold, so participation handlers run inside the unit of work's transaction, and a handler's failure comes out of the domain call.
  - A committed taggregate is read only, and read without a lock.
  - A taggregate that publishes an `ITaggregateDeletedTevent` is taken out of the store, its indexes and its storage when the unit of work commits. One added and deleted in the same unit of work writes nothing.
  - `ITaggregateIndex<TTaggregate, TKey>` files taggregates under keys their state gives, and reads its own unit of work's changes. A lookup gives its references in no particular order, as an `IReadOnlyCollection`: a caller that needs an order sorts what it finds. An index keeps no record of each taggregate's keys: a commit takes a changed taggregate's old keys from its committed instance, so a key function must give keys from the taggregate's own state alone; one that doesn't fails the unit of work, which rolls back. A store has one index for each pair of taggregate class and key type, and a second is refused where it's declared. For a moment during a commit, a lookup outside the unit of work can find a taggregate under a key its new state no longer gives.
  - A taggregate class is declared with a factory for its empty instances, `Taggregate(() => new StoredVocab())`, or, when its instances need services of the container, with a registration of the container, with as many dependencies as its constructor takes: `Taggregate(TrackedTransient.For<VocabNote>().CreatedBy((Dictionary dictionary, Readings readings) => new VocabNote(dictionary, readings)))`. The store registers it and resolves each empty instance from the container's root, so the services must be singletons: a registration that takes a scoped service, directly or through a tracked transient it takes, is refused when the container is built, with a message naming the class and the scoped service, the same with every DI container. The registration must be a `TrackedTransient`, and the class not `IDisposable`.
  - `IMemoryImageStateStore.LoadFromStorage` loads everything again while running, keeping every reference, and reports which taggregates were added, changed or removed, as collections in no particular order. `LoadFromStorage(changeTheStorageFirst)` first runs a change to the storage, such as a fast-forward of a checkout, while no unit of work is open and new ones wait. A taggregate counts as changed when the state its file holds isn't the state the store held, as the store's serializer and the consumer's options write state, so snapshot types need no equality: a file unchanged since the store last read or wrote it, by its length and last write time, is compared with nothing, and a changed one is compared with what the store would write for the taggregate it held.
  - `IMemoryImageStateStore.WriteAllToStorage()` writes every taggregate's file anew, as the store's serializer and the consumer's options write its snapshot now, as one commit through the journal, while no unit of work is open: after a change to the snapshot types or to the serializer's options, so that the files don't stay a mix of the old form and the new.
  - `ITaggregateStoreBulkReader.ReferencesToAll<TTaggregate>()` gives a reference to every taggregate of a class the memory image state store keeps, and inside a unit of work reads its own additions and deletions.
  - The store loads everything from its storage at its first use, on that use's thread and inside its transaction, if any: `LoadFromStorage()` called at the application's start chooses when. It writes each unit of work in two steps, prepare and commit. Its storage is JSON files, or memory only when none is declared. The storage seam is internal: Compze's JSON store, on the disk or on a file system in memory, covers what a consumer's own storage was for, the files in a consumer's layout and format, and in-memory storage for specifications.
  - `StoredInJsonFiles(folder, options, files => files.FolderOf<TTaggregate>(folder))` keeps the store in JSON files: a folder for each class, and a file for each taggregate, `<first two hex digits of the id>/<id>.json` in its class's folder. A file holds exactly what the consumer's `JsonSerializerOptions` make of the snapshot, in UTF-8 without a byte order mark. A unit of work's files are written all or none: each is written whole under a temporary name when the unit of work prepares, and at the commit a journal of the renames and deletions is written before any is made, so a start after a crash finishes the commit or discards it. The store's own files are in `.state-store` under the folder. For a folder that a service of the container knows, `StoredInJsonFiles((CorpusPaths paths) => paths.Corpus, options, files => ...)` resolves the service from the container's root, so it can't be scoped: a scoped one, or one that takes a scoped service, directly or through a tracked transient it takes, is refused when the container is built, with a message naming the scoped service, the same with every DI container.
  - **A unit of work that writes the JSON files can't also hold a database connection,** by default. The files and the database commit one after the other, so a crash between the two commits could lose one of the changes. Such a unit of work is refused, and rolls back: for Compze's own connections, such as the tevent store's and the exactly-once outbox's and inbox's, and for any SQL Server connection. A unit of work that only reads the store is never refused, and a container may hold this store and the tevent store. A consumer to whom that loss is acceptable declares `files.AcceptingNonAtomicCommitsWithADatabase()`.
  - **What it does when it fails or waits:** a failure after a commit's journal is written, such as a file another program holds for more than about two seconds, stops the process (`Environment.FailFast`), and the next start finishes the commit from its journal. The files are written, not flushed to the disk, so a commit outlives the process, not the machine losing its power. Its waits are fixed at 30 seconds: a get for update's for another unit of work's lock, `LoadFromStorage`'s and `WriteAllToStorage`'s for the open units of work, and a unit of work's for a load again to end; each then throws.
  - A store kept in files can start from a cache that a package of its own plugs in, such as Compze.Teventive.MemoryImageStateStore.MemoryPack's `StartingFromAMemoryPackCache()`: it reads only the files that are new, or whose length or last write time changed since the cache was written.
  - `ITaggregateJsonFiles`, which the container resolves for a store kept in JSON files, finds the way between the files and the taggregates without knowing the layout: `PathOf<TTaggregate>(id)` gives the full path of a taggregate's file, whether it exists yet or not, `PathOf(taggregate)` gives it for a taggregate in hand, by its class at runtime and its id, for code that holds taggregates of several classes through a type they share, and `TaggregateWhoseFileIs(path)` gives the class and id of the taggregate whose file a full path is, as a `TaggregateOfAFile`, or null for any other path: such as for a view of what version control lists as changed. It reads only the path, so it answers for a deleted file too. Paths are compared ignoring case, as the store compares them.
  - For specifications, in the namespace `Compze.Teventive.MemoryImageStateStore.Testing`: `files.OnAFileSystemInMemory()` puts a store's files on a file system in memory instead of on the disk: the store works as on the disk, with the same layout, the consumer's JSON options, the journal and any cache, and touches no file on the disk. A specification reads and changes the files by path through `IFileSystemInMemory`, such as to change a file behind the store before a reload.

# Rationale: Compze.Must assertion signatures

## Provenance

2026-11-12. A Deskmancer specification asserting on a `string?` registry value warned CS8620 on `TheEntry.Must().Be(…)`
and wrote `TheEntry!.Must().Be(…)` with a `todo:compze:`. Magnus had hit the same thing several times: "How to deal
with nullability differences has confused me several times in compze. Changing things only to get compilation warnings
in another situation." Compze itself carried eight `!.Must()` workarounds and five `#pragma warning disable CS8620`
files.

## The evidence

Compiled against Compze.Must 0.5.0-alpha with nullable enabled:

| Call shape | Result |
|---|---|
| `string?` `.Must().Be("x")` | CS8620: the non-generic `StringEqualityAssertions.Be` won overload resolution |
| `string` `.Must().Be(aNullableString)` | CS8604 on the expected value, same cause |
| `string?` `.Must().Contain("x")`, `StartWith`, `EndWith`, `NotContain` | CS8620 |
| `List<string>?` `.Must().HaveCount(0)`, `BeEmpty`, `NotBeEmpty`, `SequenceEqual` | CS8631: constraint `IEnumerable` |
| `List<string>?` `.Must().Contain("x")` | CS8620 |
| `int?` `.Must().NotBeNull().Actual` assigned to `int` | error: `NotBeNull` didn't narrow `Nullable<T>` |
| `string?` `.Must().NotBeNull().Be("x")` | clean: `NotBeNull` did narrow nullable references |
| `ReferenceEqual` with a `string?` expected | CS8634: constraint `class` |

At run time, a null subject made the string and comparison assertions throw `NullReferenceException` and the collection
ones `ArgumentNullException`, rather than fail.

The generic `EqualityAssertions.Be<TValue, TExpected>` had always handled every nullability correctly; only the string
overload, picked ahead of it by overload resolution, broke it.

## Alternatives rejected

- **Widening the string overload to `IAssertionContext<string?>` and a `string?` expected value.** Its return would
  then be `IAssertionContext<string?>` for non-nullable strings too, so a `Satisfy` lambda chained after it would warn.
  Deleting it makes the generic `Be` return the caller's own nullability.
- **Two overloads, one for `string` and one for `string?`.** Not expressible: they differ only in annotations, which is
  a duplicate member.
- **Relying on `NotBeNull()` alone for reference types.** It works, but makes the consumer write a step the assertion
  itself can perform, and leaves the warnings on every other call shape.
- **A nullable-value-type overload of every assertion over a value type** (`BeTrue`, `BeFalse`, `BeCloseTo`,
  `BeValidEnumValue`, six comparisons): ten more overloads for a rarer case, where the compiler gives an error, not a
  confusing warning. `NotBeNull()` narrowing `T?` to `T` covers them all.

## Why the specification compiles code

The run-time specifications can't see a signature's effect on a consumer's compiler, and Compze's own specification
projects only show it as warnings nobody is forced to read. `ConsumerCode` makes "this call shape compiles without
warnings" a failing specification. Checked by putting the old `Contain` receiver back: exactly
`Contain_narrows_the_context_to_a_non_nullable_string` failed.

## Addition: the shared primitive, and null expected values as test bugs (2026-11-12, Compze.Must 0.7.0-alpha)

A Deskmancer review of 0.6.0-alpha found that the 19 narrowing assertions each wrote `it is not null &&` in the predicate
and `!` after `RunAssertion`, with nothing tying the two, and that 7 of them had no null specification. Rather than only
add the 7 cases, the null check and the narrowing became one public primitive, `RunAssertionThatANullValueFails`, which
consumers' own assertions use too (the README had taught them the same unchecked pattern).

Magnus asked whether a null subject should instead be asserted against, as a bug in the test. Kept a failing assertion:
the subject is what the code under test produced (Deskmancer's case was a missing registry entry), so reporting it as a
test bug points at the wrong code; `Be` and `NotBeNull` already fail a null as an assertion; and the defensive-coding
rule's deciding question, "could we guarantee this state?", answers no, since Compze.Must can't guarantee what the code
under test returns. The message was made explicit instead: "was null, so StartWith had no value to check", where 0.6.0
showed only a "was null:" line among the values.

His idea did fit the expected values: a null one is the test's own mistake. 0.6.0 let .NET's own
`ArgumentNullException` escape for some (`StartWith`, `SequenceEqual`, naming .NET's parameter) and silently passed for
others (`"b".Must().BeGreaterThan(null)`, as null orders before every string). Now each asserts with Compze.Contracts.

## Addition: collection assertions take their element type from the subject (2026-11-12, Compze.Must 0.8.0-alpha)

JAStudio reported that `strings.Must().SequenceEqual(["a", "b"])` on `string?` elements warned CS8631: the signature was
`SequenceEqual<TCollection, TElement>(this IAssertionContext<TCollection?>, IEnumerable<TElement>) where TCollection :
IEnumerable<TElement>`, and C# infers `TElement` from the expected values alone, constraints being ignored by inference.

Compiled against the three candidate signatures (consumer methods with the subject as a parameter):

| Call shape | `TCollection : IEnumerable<TElement>` (0.7.0) | `TCollection : IEnumerable<TElement?>` | `IAssertionContext<IEnumerable<TElement>?>` |
|---|---|---|---|
| `List<string?>`, `["a", "b"]` | CS8631 | clean | clean |
| `List<string>`, `[]` | CS0411 | CS0411 | clean |
| `List<object>`, `["a"]` (narrower expected) | CS0311 | CS0311 | clean |
| `List<IShape>`, `[new Circle(), new Square()]` | CS0411 | CS0411 | clean |
| `ImmutableArray<int>` (a struct) | clean | clean | CS1929 |
| `.Actual` still a `List<string>` | yes | yes | no |

Magnus's first reaction was that losing the collection type is bad, so the question became how often anything needs it
after a collection assertion. A script following every `.Must()` chain in Compze, JAStudio and Deskmancer found about
1,300 collection-assertion calls: almost all end the chain, three are followed by `Contain` or `Satisfy` (which need only
the sequence), and the only `.Actual` uses were in Compze.Must's own Nullability specifications, which pin the return
type. FluentAssertions and AwesomeAssertions bind every collection through `Should<T>(this IEnumerable<T>)`, so their
`Subject` is an `IEnumerable<T>` from the first call; what assertion libraries do chain on a collection is its single
element (`ContainSingle().Which`, xUnit's `Assert.Single`, Shouldly's `ShouldHaveSingleItem`), which needs the element
type, not the collection's. Magnus approved the receiver form for every collection assertion.

Alternatives rejected:

- **`where TCollection : IEnumerable<TElement?>`.** Keeps the collection type and fixes the nullable case, but the other
  shapes still don't compile, and it can't serve an item-taking assertion: `shapes.Must().Contain(circle)` infers
  `Circle`, and `List<IShape>` fails `IEnumerable<Circle?>`. A `ContainSingle()`, with no argument to infer from, can't
  have a `TElement` at all.
- **Both signatures as overloads.** Everything compiles, but the return type then depends on whether the expected
  values settle the element type on their own: `SequenceEqual([])` returns a sequence where `SequenceEqual(["a"])`
  returns the list.

`Contain`'s overloads for `HashSet<T>`, `ISet<T>`, `IReadOnlySet<T>` and `ReadOnlyCollection<T>` went with it.
`Enumerable.Contains` asks an `ICollection<T>` itself, which every .NET set is, so a set's comparer decided either way;
the one gap, a read-only set that isn't an `ICollection<T>`, is asked by a run-time check in the single overload.
